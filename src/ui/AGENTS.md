## Purpose

Own the React DOM overlay for Factor-I.

## Ownership

- `components/` contains HUD, build dock, inspector, tech tree, notifications, prestige modal, offline modal, save recovery notice, and header.
- `hooks/` contains the external-store subscription bridge and `useModalFocus`, the one focus-trap, inert-background, and keyboard-dismissal implementation shared by every modal.
- `presentation.ts` owns machine labels, the copy for command rejection reasons, and the copy for save rejection reasons, so two components never word the same refusal differently.
- `layout.ts` owns the left-rail overlay geometry, and it is the only place those numbers live. The entity inspector and the tech tree toggle both sit on the rail at one width, so a rail constant is read rather than retyped, and the inspector's maximum height is derived from the toggle's position and the rail gap rather than chosen, so the one can never be moved past the other.
- The inspector is a bounded box that scrolls, not a content-driven box. Its height is set by its content on a machine whose fonts render shorter, and the rail below it is placed at a fixed offset, so an unbounded inspector collides with the toggle on any host with taller font metrics. It was measured overlapping on Linux while passing on macOS, which is why the bound is a contract and not a nicety.
- Every rail box sets `boxSizing: "border-box"`. Under the default `content-box`, a declared `width` or `maxHeight` bounds only the content, and padding and border are added outside it, so the inspector measured 274 px wide against the toggle's 240 px and its capped height overflowed into the toggle below. A declared size that is not the drawn size is the same class of bug as an unbounded height, so the two travel together.
- The HUD owns the two permanent-progression controls: the prestige button, which opens the confirmation modal it also renders, and the plot expansion button. Nothing else in the overlay dispatches a prestige or an expansion.

## Local Contracts

- Every refusal a shipped control can surface has its own sentence in `commandReasonMessages`, covering the unlock, upgrade, prestige, and grid expansion reasons. A missing entry falls through to `The store refused that action: <reason>.`, which shows a player an internal token, so `tests/unit/presentation.test.ts` asserts that no reachable reason reaches the fallback and that no message repeats its own reason string. A command that adds a rejection reason adds its copy in the same change.
- `notImplemented` is the copy for a command the store has not routed yet, and it stays. It is unreachable from every shipped control today, but a command added to the shared union and not yet wired is a real intermediate state during development, and a refusal from one must read as "not available yet" rather than echo the token.
- `saveRecoveryMessages` is the copy for a save the load layer refused, keyed by the persistence `SaveFailureReason` union, and the table is typed as that union so a new reason is a compile error here rather than a fallback at runtime. `getSaveRecoveryMessage` takes a plain string, because a declared reason and an unknown one have to be answerable from the same call site and a reason from a newer build must not break the notice; the table is the only exhaustiveness guard, and `tests/unit/presentation.test.ts` reads the union out of `src/persistence/migrate.ts` and fails if any member is unworded, duplicated, or contains its own reason string, so a new failure reason turns one assertion red instead of showing a player a token. Unlike a command refusal, the fallback never echoes the reason: `saveRecoveryFallback` is a plain sentence, because the reason enum is for diagnostics only. This is a type-only import of a persistence type and creates no runtime dependency from the overlay.
- The save recovery notice is a real focus-managed modal, not a toast: a player who has lost a run cannot be allowed to start playing past the explanation, and holding focus is also what keeps the recovered world unchanged behind it. It opens only from a recovery, names what happened in plain terms, and its dismissal is final for the session. Dismissal does not need to survive a reload, because a reload of an unreadable save re-reports it. The notice carries the internal `reason` and the loader's `message` as data attributes for tests and diagnostics while the visible text stays in plain terms, and it describes itself with both the summary and the cause, so a screen reader reaches the reason rather than only the fact that something failed.
- UI reads immutable `SimulationSnapshot` values through `useSyncExternalStore`.
- UI dispatches commands but never imports simulation math or mutates private store state.
- Deferred actions are visibly disabled until their simulation command exists and the action is wired. A command existing in the store is necessary but not sufficient. The tech tree wires the machine and recipe purchases, the inspector wires the level upgrade, and the HUD wires the prestige reset and the plot expansion. No control is deferred today, so a future command added to the union but not yet wired is the only case this rule still covers.
- A purchase control is enabled from the shared store preflight, `canUnlock` for a tree entry, `canUpgrade` for a level, `canResetPrestige` for a prestige, and `canExpandGrid` for a plot growth, so the affordance and the dispatch cannot disagree about whether an action is legal. The prestige modal reports a refusal from the same re-read the tech tree uses, so a stale affordance and a stale store surface a real reason instead of failing silently.
- A refused purchase surfaces the real store reason as visible text plus a `data-reason` hook. A click that the store refuses never fails silently, because a stale affordance and a stale store are a real race.
- A refused purchase is displayed from the store's current answer, never from a remembered one. A refused command publishes no snapshot, so the surface forces a re-read, and the reason shown is whatever the store's preflight says at that moment: the tech tree's alert stays up while the store still refuses that entry and clears as soon as the entry is purchasable, and the inspector's inline status simply reads the preflight. No refusal is gated on snapshot identity, because the store publishes a new snapshot every tick, so on any surface that keeps a remembered refusal an identity check would drop a true refusal within one tick. A refusal with no stated reason is shown with generic copy rather than being dropped or attributed to some other reason.
- The tech tree renders every machine and recipe from `MACHINES`, `RECIPES`, and `UNLOCKS`, orders entries by unlock cost, prices an included entry from its table `unlockCost`, and shows a locked entry's missing prerequisites. A new machine or recipe needs a content entry and nothing else.
- The offline summary opens only when `shouldShowOfflineSummary` says the session is worth reporting, so the simulation owns the threshold and the overlay never re-implements it. A summary the validator rejects is not shown at all rather than shown empty, because a load attaches a summary whenever a save is read and a first-time player reloading would otherwise be greeted with an elapsed time and an earnings total of zero.
- The prestige confirmation, the tech tree, the offline summary, and the save recovery notice are real focus-managed modals: focus moves inside on open, Tab is trapped, Escape dismisses, background content is inert while open, and focus returns to the trigger on close. The component that owns a dialog owns that dialog's lifecycle, and the mechanics live in exactly one implementation, `useModalFocus`, so a new modal wires the hook instead of copying an effect. The hook keeps only the topmost open dialog interactive, so two modals open at once cannot both consume Escape or mark each other's portal inert. `tests/unit/modalFocus.test.tsx` is where those mechanics are specified; a component spec drives its own dialog through the hook as well, which is deliberate wiring coverage for that dialog, and it must not become a second place where the mechanics are specified.
- The Factor-I header must remain visible and panels must not overlap at the supported desktop viewport, which is 1000x800. The tech tree toggle is currently pinned at a fixed `top: 400` and its bottom is 446, while the build dock's top is `viewportHeight - 126`, so the two collide below a 572px viewport height. The supported viewport is tall enough that this never fires today; any overlay work must replace the fixed offset with a flow layout rather than retune the number.
- The notification stack is anchored to the bottom right and grows upward, which is what keeps it off a HUD whose height the overlay does not measure. It was pinned below the HUD at a fixed `top: 220`, a hardcoded copy of the HUD's height that broke the moment the prestige and expansion controls made the HUD taller. It is not an unbounded guarantee: notifications are never capped, so the stack grows until it reaches the HUD, and at 1000x800 there are roughly 540px of headroom, about six to eight notifications. A run that stacks more than that will overlap, so capping the stack is the fix if a long run ever reaches it.

## Work Guidance

- Use semantic buttons, labels, and stable data-testid hooks.
- Scope pointer events to interactive controls so the canvas remains usable.
- Keep presentation formatting separate from simulation calculations.
