## Purpose

Own Playwright browser flows for Factor-I.

## Local Contracts

- Browser tests run serially for the Phaser flow and assert no uncaught page errors. `playwright.config.ts` must keep `fullyParallel` off, `workers` at 1, and `retries` at 0, so the committed config is the serial, no-retry configuration the determinism evidence was gathered under.
- Tests use real canvas interaction or the development bridge, not private state.
- Overlay layout is asserted, not assumed: `expectNoPanelOverlap` compares every pair of persistent panels, notification stack included, at the desktop viewport and reports each overlapping pair by name, so adding a panel cannot silently cover another. The six panels are read in one page-side batch rather than one locator read per panel, because the overlay's geometry is a pure function of the committed React tree and the viewport, so one pass is both the cheapest read and the only way the comparison is over a single layout state; six separate reads can straddle a layout change and cost seconds each. Because the read is page-side it cannot go through a Playwright locator, so it reproduces locator strictness itself: a selector matching zero elements or more than one is an unsettled panel with its own diagnosis, never a silent read of the first match. Each panel must be present, not `display: none` or `visibility: hidden`, and have a client rect; height is deliberately not part of that condition, because an empty notification stack would never satisfy a `height > 0` rule and would wait out the whole bound. The check locates the header by its `role="banner"` attribute in the page, so a role-based locator can no longer fail to see it behind a modal. That is not a reason to drop the old rule: still run it with the modal closed, because a focus-managed modal leaves the background inert, and measuring an inert background proves nothing about the layout a player sees. What replaces the old accessibility-tree dependency is the per-panel settled check, which fails on a panel that is present but unrendered instead of skipping it. What the check proves is the committed state at one instant, not stability across instants, because it reads one snapshot rather than two, so a panel that overlapped only between two commits would not be seen.
- Storage tests clear or seed the save deliberately and verify reload behavior.
- `support/runtimeBridge.ts` is the only shared helper for the development bridge, the telemetry bridge, and the readiness wait, and it holds the one `declare global` every spec should import rather than copy. Two files may each declare `interface Window` for the same property and the declarations merge, so the constraint is not a duplicate declaration but a differing type: a redeclared property has to have the identical type, and the local `RuntimeBridge` in `phase0.spec.ts` declared a wider snapshot shape, so a second spec that declared the same window property against its own copy of those interfaces would have failed to typecheck rather than merged. A spec still opens its own `pageerror` and `console` listeners inline, so do not read this module as the single place browser errors are watched.
- A save the load path refuses has to be seeded as raw JSON through `addInitScript`, because a save the game cannot read cannot pass `serializeSave`, which validates before it writes. The seeded shape is a save the run could have earned but this run did not, such as an expanded plot with no completed prestige, so the rejection is the load layer's verdict about a real field rather than an invented corruption.
- The save recovery flow is proven by what the player sees and by what storage holds, and both matter: the notice must be up with the real reason and the loader's message, the run must have actually started fresh rather than only claiming to, and the stored bytes must still be the seeded bytes after a real state change made while the notice is up. Asserting the payload only before anything changed would pass with no write suppression at all, because a fresh run projects the same value and structure the autosave was seeded with, so an untouched recovered run no-ops every write attempt. The state change has to be one the save records, since a change that only touches runtime state, such as a selection or a placement mode, does not alter the projection and writes nothing either way.
- The dismissal half of that flow is asserted too, so suppression cannot be implemented as autosave simply being broken: after the notice closes, the next structural change is written and the stored save is the recovered one.
- A load with no refusal is the regression guard and is asserted in the same spec, once for a stored save that reads into the run and once for a player who has never had a save. Both assert the notice is absent and that the world proves which of the two cases it was.
- A saved world that the runtime is supposed to honour is proven by seeding it through `addInitScript` under `SAVE_KEY`, reloading, waiting for ready, and reading a value the renderer derived from it. A camera bound is the observable for plot size, and it must be read from the camera rather than from the value the scene intended to configure, or the assertion passes whether or not the scene applied it. A seeded plot larger than the starting one must also be one the run earned, so a save claiming expanded area is seeded with a completed prestige; a bare `createInitialState()` widened past the starting plot is a forged save, and seeding it now fails at `serializeSave` rather than proving anything about the renderer.
- The browser layer is the last place a recovery guard can be proven. Seeding a plot far outside the contract must reach ready with the starting plot and the starting currency, because a world that trusts an unbounded saved dimension builds a tilemap that never yields. Here the per-test budget is the hang detector, which is the browser form of the wall-clock contract in `tests/unit/AGENTS.md`, so the test asserts readiness rather than timing out.
- Seeding any save opens the offline summary modal, because the load path attaches a summary to the credited state whatever the elapsed time was. A browser flow that seeds a save and then drives the overlay dismisses it first with a real click on its own `data-testid`; a flow that never seeded a save sees no modal, which is why a seeded flow can fail only against a spec that starts from storage.
- No arbitrary sleeps; use condition polling, rAF synchronization, or deterministic bridge ticks.
- Render telemetry is published from the scene update, so it trails the simulation by the events of the current tick. Read it only after a frame boundary, and never gate a frame wait on a telemetry value read earlier in the same tick; a scan that advances a tick and then reads render state synchronously steps over short-lived windows such as a belt item in flight. A state that persists, such as a blocked producer, may be scanned in batches of several ticks per frame instead.
- A geometry read such as `boundingBox` auto-waits for the element to be attached but then reads the box once, so it returns `null` while an attached element has no layout yet. Poll until a box exists, and pass an explicit timeout plus a label so a failure names the element instead of waiting out the whole test deadline. The explicit bound has to reach the read itself, not just the poll around it: `boundingBox()` with no options takes an unbounded timeout, so the read runs until the test runner kills the run at 30,000 ms, and a poll that only checks its own deadline after a read returns is therefore not bounded at all. `waitForBoundingBox` passes its remaining budget to `boundingBox({ timeout })` on every attempt for that reason, and its default is 10,000 ms rather than the 5,000 ms it replaces because the old 5,000 ms was a race against a read that had no bound of its own, so it fired on the cost of a single read rather than on a real absence; 10,000 ms stays far above one read, so the bound reports a panel that genuinely never appears and not one that is merely slow. A failure from either wait names the panel, the wait, and the element's observed state, because Playwright's own `expect.poll` timeout names none of them: `expect.poll` throws its own TimeoutError before the helper's message can run, and when the first poll attempt loses the race to the deadline its `lastResult` is still undefined, so the emitted message is only the timeout line and no panel name can appear at all.
- The runtime's own fixed-step clock keeps selling between Playwright round trips, so a currency read in one `evaluate` and another in the next include whatever sales landed in between. Read currency on both sides of a dispatch inside the same `evaluate` and assert the exact debit from that pair; never difference two separate reads.
- An unlock purchase whose debit must be exact is driven by a real DOM `click()` on the control's own `data-testid` from inside the page, after Playwright has asserted the affordance with `data-cost`, `data-state`, and enabled. That keeps the read-click-read atomic; the surrounding modal lifecycle is still driven with Playwright locators, and the committed unlock is proven from the store snapshot, the entry state, and the unlock notification.
- A React readout trails the store by a render, so a rendered value is compared toward a bridge value the store has already reached with `expect.poll(...).toBeGreaterThanOrEqual(...)`, never by equality against a bridge read taken afterwards.
- A long manual-tick run advances in bounded chunks with a frame boundary between them. Every sale adds a spark sprite whose tween retires only while the game loop runs, so one unbounded `advanceTicks` leaves thousands of live sprites behind; chunking with a double `requestAnimationFrame` is what keeps a long economy run cheap.
- Render telemetry shows a belt item at a tick boundary only when at least three belt cells separate the producer from the consuming machine's input port cell. A producer's push and the consumer's pull otherwise land in the same tick, so a one- or two-belt run is invisible in telemetry even though the chain is working. Size the run for the observation, not the other way round.
- Machine ports are offset geometry rather than cell occupancy, so a chain connects only when each machine's rotation puts the expected ports on the expected faces. A persisted `rotation` together with a traced production chain whose `outputResource` is the chain's last product is the proof that the rotated ports resolved; there is no negative assertion to write for the unrotated layout.
- A bulk removal is proven at the render seam, not at the store: a prestige empties the scene only if the browser stops drawing, hit-testing, and reporting the entities it removed, so the assertion reads the scene telemetry's `entityIds` and `activeEntityIds` and both must be empty. The store's event stream is not a substitute, because the scene's bookkeeping only moves on render events.
- Playwright's per-test timeout is a wall-clock budget, not a work budget. A spec that plays a whole economy through thousands of deterministic ticks sets `test.setTimeout` explicitly instead of trimming the chain it is proving.
- The panel-overlap flakiness has a diagnosed cause, and the mechanism is now a contract rather than a suspicion. The renderer main thread is saturated by the Phaser loop plus an overlay that re-renders on every store tick, so every Playwright operation against this app queues behind long tasks: a bare `page.evaluate` round trip costs about 120 ms against 3 ms on a static page, and a locator geometry read costs about 1.2 s at the median with a tail past 3 s on this app with no injected load, rising past 4 s under load. A geometry assertion in this suite must therefore be written as one batched page-side read, and must not be written as one locator read per element. `tests/e2e/overlayLayout.spec.ts` holds that as an executable contract: it fails a panel the old helper could only report as a generic predicate timeout, it proves the assertion still names an overlapping pair after a real overlap is forced, it proves an ambiguous selector is reported rather than silently read once, and it proves the check survives a renderer main thread saturated to 600 ms per frame, a load at which the old six-read sweep timed out every panel and cost about 57 s against the new check's 6.4 s. That saturation test's only real bound is the 30 s per-test timeout rather than an explicit one, so its margin over the observed 6.4 s is roughly fivefold; a regression in the read would show up as that test approaching the per-test budget, not as a fast clean failure.
- The remaining readiness wait is a wall-clock wait and can time out on a loaded machine while every assertion about the game is still correct: `waitForReady` polls a 5 s predicate. Re-run a single failure once to separate it from a repeat, then treat a repeat failure, or any failure in an area the change touched, as a regression rather than a flake. A `waitForReady` timeout in particular is the signature of a load or validation regression, not of host load, because a world that fails to start is exactly what that wait exists to catch. Host load is still a real confounder for wall-clock budgets: on an oversubscribed host the whole suite can fail on 30 s test timeouts unrelated to any change, so a baseline run on the same host is the only fair comparison before blaming a diff.
