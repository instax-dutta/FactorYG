## Purpose

Own deterministic Factor-I simulation state and production rules.

## Ownership

- `types.ts` defines the simulation and save-facing contracts.
- `constants.ts` locks tick, grid, tile, and save-key constants. Every number that prices progression lives in `content/balance.ts` instead, so the simulation never restates a balance value and the content module stays the single place one is tuned.
- `grid.ts` and `rotation.ts` own coordinate transforms, and `grid.ts` also owns the grid expansion geometry rules and the plot-rights predicate, so the command layer never repeats a dimension bound. The predicate is declared once as `hasPrestigedForExpansion` over a prestige count, and both the command layer and save validation read it, so the two cannot answer the question of who may own a larger plot differently.
- `placement.ts` and `connections.ts` own validation and port connectivity.
- `machines.ts`, `economy.ts`, `tick.ts`, and `offline.ts` own production and sales, and `tick.ts` sells through the sale terminals the machine table declares.
- `chains.ts` owns production chain discovery, steady-state throughput, and `getDrainableEntityIds`, the reachability verdict the blocked path reads. It answers on the same `buildSuccessors` graph the chain analysis walks, so the two cannot disagree about what is wired to what.
- `prestige.ts` owns the prestige points formula, the single eligibility validator, `permanentMultipliersForPoints`, the one derivation from a banked point count to a permanent multiplier pair, and `repairPermanentMultipliers`, which rewrites a stored pair that disagrees with the points behind it. The snapshot's `prestigeReady` flag reads the validator instead of repeating the threshold.
- `commands.ts` owns unlock purchases for machines and recipes, the entity level upgrade, the prestige reset with its `canResetPrestige` preflight and `getPermanentMultipliers` read, and the grid expansion with its `canExpandGrid` preflight and its `GRID_EXPANSION_COST` debit.
- `store.ts` owns private state, commands, snapshots, the fixed-step driver, and the read-only `getActiveMachineIds`, `getBlockedMachineIds`, and `getGridDimensions` views a renderer reads instead of simulating.
- `initialState.ts` owns deterministic new-game world creation, `createExpansionNodes` for the area a plot gains, and `createResetState`, the one constructor for a post-prestige world. `NEW_GAME_SEED` is the single seed both a new game and an expansion scatter from, so the same world always produces the same nodes. Resource nodes are scattered across the whole grid, rather than banded into quadrants, so a straight belt line can carry any resource to any part of the map. Banded nodes made the deep production chain arithmetically unreachable: a two-raw smelter could only be fed from one band, and no two bands overlapped.

## Local Contracts

- Simulation modules are pure TypeScript and never import React, Phaser, DOM, or persistence.
- Production advances on a fixed 10 Hz logical clock, never Phaser render frames.
- Runtime-only fields such as tick samples and offline summaries are not save data; `bufferedResource` and `alreadyNotifiedBlocked` are save data, and the `blockedRefusalTicks` stuck-tick debounce counter is runtime-only and is never projected, so a reloaded machine is judged from the world it loads into rather than from a counter it did not save.
- Extractor progress counts unemitted whole cycles plus the fractional cycle: a full output buffer pauses progress, a partly filled buffer accepts as many whole cycles as fit in that tick and banks the rest, and the bank is capped at the machine's output capacity, so the progress the save stores is always bounded and drains the instant a slot frees. At a per-tick rate of one cycle or more, credit past that cap is discarded rather than banked.
- Processor progress is a discrete recipe-tick counter; inputs are charged once when a run starts, a blocked completion holds the counter only while the recipe remains valid, and an unresolvable recipe discards the run so a later run must pay again.
- A silo is shared storage, not a processor: the first accepted resource locks in `bufferedResource` until the shared pool empties, capacity is enforced exactly at the acceptance boundary, and a refused acceptance consumes nothing.
- A machine-to-belt transfer withdraws only what one belt cell can carry and leaves the remainder buffered, so a push never destroys units.
- A machine-to-machine transfer accepts only the input room the target has left for that resource and leaves the remainder buffered. For `separate` buffers `inputBuffer` is a per-resource limit, not a buffer total, so a mixed buffer may hold several times the table value. A transfer that fits no unit is refused and changes neither machine. Shared storage stays all-or-nothing, so a shared target also refuses a partially fitting transfer even when room remains.
- `storageFull` is emitted on the transition into a full shared pool, never on every tick it stays full.
- A machine that cannot hand off goods to its connected target is a candidate for blocked, and `alreadyNotifiedBlocked` is the save-data record of a confirmed block. A machine is a candidate when it holds at least one unit of a storable resource, has a connected target, and that target accepts none of what it offers, whether the target is a full shared pool, a full input buffer, or an occupied belt cell. A machine with no target at all is buffering, not blocked, and a machine that transfers anything at all is never blocked on that tick, so a mixed buffer that moves one resource while another is refused stays unflagged.
- A refusal is only a block when the line can never drain again, and drainability is what separates the two, not how long the refusal has lasted. A refused producer is stuck when its line is undrainable, which is `getDrainableEntityIds` reporting its id absent. That verdict is structural rather than timed, so a saturated but healthy line is never flagged no matter how deep, how slow, or how high a level the chain runs at, and a line that has not sold yet is never flagged either, because a line that cannot drain is one with nowhere to drain to rather than one that has been slow.
- A machine is undrainable when no path from it reaches a sale terminal through machines that can actually run, and `getDrainableEntityIds` decides that in one reverse breadth-first walk from the world's sale terminals over the same port-validated edges chain analysis uses. A sale terminal drains because it sells everything it receives. A belt or silo drains because it only transports. A producer drains when its consumer drains. A smelter or assembler drains only when it holds a recipe its own machine type can run and every one of that recipe's inputs is producible in this world, so a machine that can never start a run is a wall rather than a step. A processor with no runnable recipe has no output port edge in the graph at all, so a consumer that holds no recipe, or one that names a recipe its machine type cannot run, already terminates the walk without a special case. An input nothing produces is decided by a fixpoint over the world's own recipes, seeded from the extractors standing on their nodes, so `ironIngot` is not producible in a world with no coal and the machine naming it is a wall.
- The verdict is deliberately conservative in the direction of silence, because the cost of a false report is a healthy line told it is broken. A chain is only reported undrainable when nothing in it can ever move; a producer whose input is obtainable but whose goods are not yet routed to it is treated as drainable and left unflagged rather than guessing. Restoring what a machine was missing, or reconnecting it, changes the verdict on the next tick and the flag clears on its own, so the block reports a fault the player can fix rather than a verdict they must clear by hand.
- `getProcessorRecipe` in `machines.ts` is the one resolver for whether a processor can run a recipe, checking that a recipe is named, unlocked, and one the machine's own type can run. The tick calls it to decide whether a machine advances and the drainability analysis calls it to decide whether it is a wall, so a machine can never run a recipe the blocked path believes it cannot, and neither caller restates the three conditions.
- A refusal is debounced before it is a block. The flag is set only after `BLOCKED_REFUSAL_TICKS_REQUIRED` consecutive stuck ticks, which is two, so one unlucky tick is never a report. The counter counts stuck ticks rather than raw refusals, so a live line that refuses every tick leaves it at zero instead of parking it at the threshold, and the counter is capped at the threshold so a long block cannot grow without bound. It is cleared the moment the machine moves anything or the line becomes drainable again, so demolishing the refusing target clears the block.
- The drainability verdict is recomputed once per tick before any machine output is transferred, so it reads one world state rather than a half-transferred one and the flag cannot depend on the order machines happen to be walked in. It is a single reverse walk over the port graph and a recipe fixpoint, both linear in the world, so the cost of the answer is the cost of one tick's own traversal rather than a per-machine rescan.
- A confirmed block survives a reload through `alreadyNotifiedBlocked`, and a reloaded blocked machine stays flagged without re-announcing itself, so the renderer resumes the blink and never emits a duplicate `blockedFull`. The verdict is re-derived from the loaded world on the next tick rather than trusted from the save, so a load that repaired the fault in the world clears the blink and a load that preserved the fault keeps it.
- `blockedFull` is emitted on the transition into a blocked producer and never again while it stays blocked. It is about the refused producer, not the refusing target: a full silo emits `storageFull` for itself and `blockedFull` for the machine pushing into it, and a blocked producer is not necessarily the machine that is full.
- Blocked feedback needs no belt state. `moveBelts` refuses a cell that is occupied at the start of the tick, so a jam already propagates backward through a line and every item stays where it was. Running the machine handoff before or after `moveBelts` makes no difference to a saturated line: the line settles into one travelling hole, so the head cell is occupied on all but one tick in `N` however the two steps are ordered. Neither the ordering nor the debounce is what separates a jam from a saturated line, though; only the drainability verdict is, and it reads no belt contents at all, so the separation cannot depend on a jam that has not propagated yet.
- Blocked feedback is a red blink on the refused producer and nothing more. The renderer reacts to `blockedFull` by blinking the machine and never to a belt state, conveyor clogging stays emergent from what the belts hold, and the event is a transition rather than a level so a later transient-on-transition sound lands once per block instead of once per tick.
- An unlock purchase validates identity, prior ownership, prerequisites, and cost before any mutation, then commits the currency debit, the unlocked ID, and one success notification in a single state transition, so a purchase can never debit without unlocking or unlock without debiting.
- Unlock rejection reasons are `unknownUnlock`, `alreadyUnlocked`, `prerequisiteLocked`, and `insufficientCurrency`, and the prerequisite reason is reported before the balance reason. A rejection returns the same state object, so no snapshot and no notification is published.
- An unlock notification is keyed `unlock-machine-<id>` or `unlock-recipe-<id>` and stamps `createdAt` from the logical `tickCount`, keeping notifications deterministic.
- An upgrade prices the level being left as `baseCost * level * level` from the machine cost table, validates identity, machine type, and cost before any mutation, then commits the currency debit, the level increase, and one success notification in a single state transition, so an upgrade can never debit without raising the level or raise the level without debiting.
- Upgrade rejection reasons are `entityNotFound`, `unsupportedMachine`, and `insufficientCurrency`, reported in that order. `unsupportedMachine` covers every machine type a level cannot affect, so a machine that only transports or stores can never be bought for nothing. A rejection returns the same state object, so no snapshot and no notification is published.
- An upgrade notification is keyed `upgrade-<entityId>-l<level>`, names the new level, and stamps `createdAt` from the logical `tickCount`. The level belongs in the key because one entity can be upgraded repeatedly, so a key that is stable per entity would collide as a render key, repeat a `data-testid`, and make one dismiss remove every message for that entity.
- The store routes the `upgradeEntity` command to `upgradeEntity` and exposes `canUpgrade(entityId)`, so the ghost preview and the dispatch share one validator.
- The level scales the extractor rate, the processor effective duration, and the machine output capacity. The extractor rate is uncapped, so a level above the table interval emits more than one unit per tick instead of buying a dead level, while the effective duration still saturates at one tick. The effective duration stays a whole number of recipe ticks, so processor progress remains a discrete counter, inputs are still charged once per run, and an upgrade applied to an in-flight run shortens that run instead of restarting it.
- A sale terminal is declared in the machine table with `saleTerminal`, and both the sales tick and chain analysis read that flag instead of naming a machine type, so a new selling machine needs a content entry and nothing else.
- An extractor is `active` on every tick its output buffer is not full, whether or not a cycle completed, so a machine state event fires once when a full buffer pauses it and once when it resumes; a processor keeps its own per-run meaning.
- A sale sample records the tick, the currency earned, the machine that sold, and the resource it sold, so the rolling window can be read per machine and per resource. The extra fields are runtime-only and are never save data.
- Chain analysis follows only valid directed port connections from `connections.ts` and never grid adjacency: a machine links to the machine standing on its output port only when `arePortsConnected` accepts the pair, and a belt link is validated with the item the belt is carrying, the same argument the deposit step passes, so the analyzer never walks a link the simulation would refuse. A belt holding nothing is linked by port geometry alone, which is what a belt-to-belt move already assumes.
- A chain is a maximal directed path keyed `chain-<firstEntityId>`, and results are ordered by chain id. A path with no producer reports no chain, so a bare belt or depot is not a production chain, and two branches stay separate because each is keyed by its own first entity rather than merged by resource.
- A directed cycle has no root, so every member of a cycle starts its own chain, cut at the machine that closes the loop, and a cycle reports one chain per member rather than collapsing into one and dropping the rest. A machine with more than one successor is walked through its first successor in sorted order, which is exact today because every shipped machine has at most one output port and becomes a documented limit the day one does not.
- A cell that holds two entities belongs to the first entity id in sorted order, so a corrupt or overlapping world analyzes the same way whatever order its entity list uses.
- A chain's output resource is what its last producer emits, which is the resource a terminal sale sells, and a chain that reaches no sale reports zero throughput.
- Each sale terminal belongs to exactly one chain, the claiming chain whose id sorts first, so a terminal several branches reach is measured once and the summed chain throughputs equal the world's real rate. Chains stay distinct and every other claimant reports zero.
- `steadyStateThroughput` is realized output units per second, measured from the rolling window in `economy.ts` as the currency a chain's own claimed sale terminal recorded, divided by the resource sell value, the permanent sell multiplier, and the window length. It is zero before a full window exists and is never a static table rate, and `getSteadyStateThroughput` is the sum of the chain throughputs.
- The store's save view is the live state, because the runtime save path measures chains from the rolling window, while `projectSaveGame` still writes only `SaveGame` fields.
- Level one is the identity for the level model: an unupgraded machine keeps its table rate, its table recipe duration, and its table output capacity. `canRunRecipe`, `consumeRecipeInputs`, and `completeRecipe` take the entity rather than a level, so no caller can read an unleveled capacity by omitting an argument.
- Prestige points are `floor(sqrt(lifetimeCurrency / PRESTIGE_THRESHOLD))`, dividing by the one shared `PRESTIGE_THRESHOLD` in `content/balance.ts` rather than a private literal, so a second threshold definition cannot drift. The formula floors, so the first point lands exactly at the threshold, each later point needs a whole perfect square of the scaled lifetime, and a value just below a square still earns the lower count rather than a rounded one.
- Points and eligibility are separate rules. `canPrestige` is true from the threshold inclusive, so a state at the threshold and one just above it are both eligible, and it reads lifetime currency while ignoring the spendable balance, because spending currency never lowers lifetime currency.
- A lifetime that is negative or not finite is unusable rather than large. `calculatePrestigePoints` returns zero instead of `NaN` or a negative count, and `canPrestige` is false, so a corrupt save can never be prestige-eligible for a payout worth nothing. Both reject on one finite non-negative check rather than special-casing each bad value.
- Prestige points and eligibility read no clock and no random source, so one lifetime value always produces the same points and the same eligibility answer.
- A prestige reset validates eligibility through `canResetPrestige`, which reads the same `canPrestige` validator the snapshot and the preflight accessor use, and it commits the whole reset in one state transition. A rejection returns the same state object, so no snapshot and no notification is published, and the refusal reason is `insufficientLifetimeCurrency`.
- The reset state is built by `createResetState` from a fresh initial world at the surviving plot size, so the currency returns to `STARTING_CURRENCY`, the grid entities, machine runtimes, belts, resource nodes, and chain summaries are dropped, the entity sequence, tick count, and sale samples restart, and selection, placement mode, and the offline summary are cleared. The pre-existing state is never mutated, because the reset constructs a new world rather than emptying the old one.
- Only the prestige block and the plot size survive a reset. Points, the prestige count, the permanent multipliers, and the player's expanded width and height are banked into the new world; lifetime currency, spendable currency, paid unlocks, levels, and the built entities are not, so a paid machine must be purchased again and the free starting unlock set is restored. The dimensions survive because a plot is a permanent privilege: a reset that rebuilt the starting grid would charge the player a second time for area they already own. `createResetState` therefore takes the surviving dimensions and rebuilds a fresh world at that size, and the node scatter is regenerated across the whole surviving plot.
- Grid expansion survives a prestige reset. This was a balance decision parked by Task 3.2 and settled here, and it is what makes expansion worth selling: Task 3.4 prices a permanent privilege, so the privilege has to persist. The dimensions are the only part of the grid that survives, and they are rebuilt rather than reused, so a reset world is a valid new world at the old size.
- Expansion is a permanent privilege granted by the permanent-progress block. `isGridExpansionUnlocked` is the one gate, and it is the conjunction of its two documented halves: `hasGridExpansionRights`, true from a run's first completed prestige for good, and `canAffordGridExpansion`, the run's spendable currency reaching `GRID_EXPANSION_COST` from `content/balance.ts`. `canExpandGrid` consults the halves in its documented order so each refusal is named, and its last check is the gate itself, so the two halves cannot drift into a second independent gate. `tests/unit/expansion.test.ts` pins the gate to the command's verdict for a run with rights and money, a run that cannot pay, and a run with money and no rights, so the affordance and the dispatch provably cannot disagree.
- The rights half is a permanent privilege, so it is enforced on the way back in as well as on the way out. `src/persistence` refuses a saved plot larger than the starting one unless the run has expansion rights, reading the same predicate, so the load layer and the command layer agree about who may own a larger plot. Because the privilege is permanent and a reset banks both the plot and the prestige count, the rule can never reject a save the game produced, and it is a save-integrity rule rather than a crash guard: an out-of-contract size is the hang, an unearned one is silent. It is not an anti-cheat measure, since the only surface that can present such a save is the player's own localStorage and the same player controls the prestige count too.
- The expansion cost is spendable currency debited in the same state transition that grows the plot, so a growth can never commit without its price or a price without its area. It is the same price for every step and is never refunded, and because a reset hands back only `STARTING_CURRENCY` a player always pays for each growth again out of the run that grew it.
- An expansion validates before it mutates, and the reasons are reported in this order: `outOfRange` for a dimension that is not a whole number of cells or falls outside `GRID_MIN_SIZE` through `GRID_MAX_SIZE`, `invalidGridStep` for a dimension that is not a whole number of `GRID_EXPANSION_STEP` cells, `expansionLocked`, `gridShrink` for a dimension below the current one, `gridAlreadyExpanded` for a request that grows nothing, `entityOutOfBounds`, `nodeOutOfBounds`, and finally `insufficientExpansionCost`. Dimension validity is checked before the unlock so a malformed request is malformed for a run at any progress, and the price is checked last so every structural refusal about the request or the world is reported before a financial one. A rejection returns the same state object, so no snapshot and no notification is published.
- A dimension is legal only as a whole number of `GRID_EXPANSION_STEP` cells, which keeps every plot a whole number of half-starting-plot blocks and keeps the floor tilemap on whole tiles. The bounds are `GRID_MIN_SIZE`, the smaller starting axis, and `GRID_MAX_SIZE`, four times the larger starting axis, so a corrupted or hostile dimension cannot ask for an unbounded world and the derivation stays correct if the starting plot ever becomes rectangular. Both are derived from the two starting dimensions rather than hardcoded, so neither bound can drift from the world a new game creates.
- A plot grows only upward and rightward from its origin, so an existing entity never moves and a saved coordinate never changes meaning. The origin and the new far edge are both proven usable after a growth, rather than inferred from the dimensions: a placement on the origin cell and on the last new cell is accepted and one cell beyond the new edge is `outOfBounds`, so the boundary a player is given is the boundary the simulation enforces. Every existing entity and every existing resource node is revalidated against the new bounds before the change commits, so a world that already disagrees with its own grid is refused rather than carried into a larger one.
- A valid expansion commits the new dimensions and the new nodes in one state transition, and it leaves the entity list, the machine and belt record maps, and the chain summaries as the same object references rather than rebuilding them, so a runtime the tick loop is already walking cannot be swapped underneath it. It emits no render event: no sprite changes, and the floor and the camera bounds are renderer state the scene reconciles from the store.
- An expansion never moves an existing node, because an extractor stands on the cell its node was on and a reshuffled world would leave that extractor over empty ground. It appends only the nodes the new area needs, and the count per raw type scales with area rather than staying at the starting eight, so density does not fall as the plot grows and a reset world scatters the same number a grown plot would have.
- The store routes the `expandGrid` command to `expandGrid` and exposes `canExpandGrid(width, height)` and `getGridDimensions()`, so the expansion control and the dispatch share one validator and the renderer reads the plot size instead of a constant. The snapshot publishes `gridWidth` and `gridHeight` so the control names the next plot size from the store instead of its own arithmetic, and `expansionRights` from `hasGridExpansionRights` alone, because the modal's copy asks whether the run has ever prestiged and must not be answered by the affordability half. The control's own affordance is the preflight, not the snapshot.
- The stored `prestige.permanentMultipliers` pair is the single source of truth the simulation reads: `getExtractorRate`, `sellResource`, `calculateOfflineProgress`, chain throughput, the store's `getPermanentMultipliers`, and the prestige preview all read that field, so no consumer can price a run differently from another. A getter that re-derived the pair from the point count would be a second source of truth, so `getPermanentMultipliers` returns the field and nothing else.
- The rule that decides what the field must be is `permanentMultipliersForPoints`, `1 + points * PRESTIGE_PRODUCTION_BONUS_PER_POINT` and `1 + points * PRESTIGE_SELL_BONUS_PER_POINT`, declared once in `prestige.ts`. Only three modules call it, and each for one reason. `prestige.ts` calls it in `repairPermanentMultipliers`, which recomputes the pair on load, and in the rule's own definition. `initialState.ts` calls it in `createInitialState` and `createResetState`, and those two are the only places that write the field for a new game or a reset world. `snapshot.ts` calls it to publish `prestigeNextMultipliers`, which is a read for the preview and is why the preview cannot disagree with the award. The command layer never calls it, so `createResetState` is the only writer on the reset path and no caller can hand a reset world a stale pair.
- `repairPermanentMultipliers` is what keeps the two from drifting when the balance numbers move. A save written under older numbers still carries a pair priced by the old constants, so loading one recomputes the pair from the points the player actually banked and a run is never priced by a number the current balance does not produce. It returns the same state object when the pair already agrees, so a current save is not reallocated, and it never mutates the state it repairs. The offline payout is computed from the repaired state, so an offline session cannot be paid at the stale price either.
- The preview is the award. The snapshot publishes `prestigeAwardPoints` and `prestigeNextMultipliers` from the same derivation a reset writes, so the pair a player is shown before confirming is the pair the store holds afterwards, and `tests/unit/permanentMultipliers.test.ts` asserts the previewed sale and extraction rates against the ones the reset actually produced. Because nothing multiplies the running state, the award still lands once per reset rather than once per read or per tick.
- A reset is a bulk removal, so it emits one `entityRemoved` event per removed entity, in the order the old world held them, and a renderer that only reacts to `entityPlaced` and `entityRemoved` must still end up with an empty scene. The scene's sprite, blink, active, belt-item, and hit-test bookkeeping all live behind `entityRemoved`, so a command that clears the world without publishing those events leaves the browser drawing a run that no longer exists. The store publishes the rebuilt snapshot before the events, so a renderer reconciles the new world before it tears the old one down, and a rejected reset publishes no events at all.
- The reset world is immediately serializable: every machine and belt record belongs to a surviving entity because the world is rebuilt whole, so a save written straight after a reset validates rather than failing on a dangling reference. The rebuilt world carries the new-game `lastSavedAt`, so it cannot claim offline time on its own.
- The store routes the `prestige` command to `performPrestige` and exposes `canResetPrestige()` and `getPermanentMultipliers()`, so the reset button and the dispatch cannot disagree. The snapshot publishes `prestigePoints`, `prestigeReady`, `permanentMultipliers`, `prestigeAwardPoints`, and `prestigeNextMultipliers` so the confirmation modal renders entirely from the snapshot and imports no simulation math.
- Content tables and shared types remain the single source of truth.
